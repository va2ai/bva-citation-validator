# PROOF — What This Repository Actually Demonstrates

This file exists to keep the README honest. The README describes a production
reliability pattern; this file says exactly what is reproducible in this
repository versus what came out of the production system it was distilled from.

## What you can reproduce locally

With `ANTHROPIC_API_KEY` set, the following are reproducible end-to-end from
this codebase:

1. **Sentinel-tagged retrieval context.** `lib/context.js` ships a fixed
   six-document fixture (three CFR sections, three BVA decisions, one of which
   is deliberately marked `superseded`). The fixture is the same one used by
   the CLI, the web GUI, the fix suite, and the regression runner.

2. **Grounded vs. ungrounded generation.** Run
   `node validator.js` (grounded) and `node validator.js --ungrounded` against
   the same fixture and the same query. The ungrounded mode removes the
   citation-discipline rules in the system prompt, and the validator's
   output reliably shows interpolated or fabricated identifiers that do not
   appear in the source packet. See `docs/eval-notes.md` for representative
   output of both runs.

3. **Five-layer pipeline.** The pipeline runs in the order shown in
   `docs/architecture.md`: generation → extraction (JSON-schema enforced) →
   deterministic cross-reference → adversarial critic → optional prompt
   advisor. Each step writes a structured event to `logs/sessions.jsonl`.

4. **Status taxonomy.** `lib/validate.js` emits one of `VERIFIED`,
   `OUTDATED`, `NOT_IN_SOURCES`, `UNGROUNDED`, or `HALLUCINATED` per
   extracted citation. `UNGROUNDED` and `HALLUCINATED` are only
   distinguishable when `BVA_API_URL` is set; otherwise unverified citations
   surface as `NOT_IN_SOURCES`.

5. **Adversarial critic.** `critic.js` runs a Haiku pass with a fixed JSON
   schema over the response, sources, and validation report. It is designed
   to surface issues that string-match validation cannot catch (overstated
   claims, temporal assumptions, misleading use of a real citation).

6. **Recursive prompt optimization.** `lib/prompt-loop.js` runs the
   ratchet loop across the four `TEST_QUERIES` in `lib/context.js`, scores
   each candidate prompt with the composite metric in `computeScore()`, and
   keeps or reverts based on score delta. State is persisted to
   `optimize/state.json` for crash recovery.

7. **Regression cases.** `tests/regression/cases/*.json` freezes four known
   failure modes — context-boundary confusion, interpolated identifier,
   outdated citation, fabricated docket — and `tests/regression/runner.js`
   asserts that the pipeline still catches each one.

## What is NOT reproducible from this repository

The README cites a four-week internal monitoring window with a reduction
from roughly 15 percent of sessions containing detected citation hallucinations
to under 1.5 percent. Those numbers come from a **separate, private system**
(V2V Intelligence, backed by a corpus of 1.85 M+ BVA documents, real user
sessions, and live MCP retrieval). They are not generated by anything in
this repository, and this repository contains no production data, no user
queries, and no API credentials.

Concretely, the following are **not** in this repo:

* The 1.85 M-document BVA corpus and its retrieval index.
* The MCP retrieval tools that populate the sentinel-tagged source packet
  in production (`bva_cfr_section`, `bva_search`, `bva_cavc_search`, etc.).
* Real user queries or session logs.
* The dashboard that produced the 15% → <1.5% measurement.
* Any API URL for the live verification endpoint (`BVA_API_URL` is left
  unset by default; the validator works without it).

The metric is also **scoped narrowly**: it counts sessions in which the
validator detected fabricated or unsupported structured references, under
this validator's definitions. It does not measure legal correctness, user
satisfaction, or any guarantee that no hallucination of any kind reaches a
user. See `docs/eval-notes.md` for a fuller treatment.

## Boundary on the domain

The validator answers exactly one question per claim: *does this identifier
appear in the retrieved source packet, and is the metadata fresh?* It does
not determine whether a citation is legally correct, whether a BVA decision
was correctly decided, whether a CFR section is the right authority for a
given fact pattern, or whether the model's reasoning is sound legal
analysis. The adversarial critic surfaces some reasoning issues, but it is
itself an LLM and is not a substitute for review by a VA-accredited
attorney, agent, or VSO representative.

## What "production-derived" means in the README

The architecture in this repo was distilled from failure analysis in a
private production system. The failure-mode taxonomy in
`docs/failure-modes.md`, the sentinel-tag design, the deterministic
validation layer, the critic pass, and the regression discipline all came
out of that failure analysis. The code in this repository is a clean-room
reimplementation against a small public-style fixture, not an export of the
production code.

If you want to reuse the pattern, the right way to read this repo is:
the architecture is the artifact, the fixture is just enough to exercise it.
